# generate-client

Turns the Chat Generator spec into a working client for one **target**. The same procedure
serves interactive use (`/generate-client web`) and headless use
(`node harness/regen.mjs web`, which runs step 1 itself and then hands you this file).

**Target:** `$ARGUMENTS` (if empty, ask which of `harness/targets/*.json` to use).

## Non-negotiable rules

1. **The spec is the source of truth.** Implement exactly what the spec bundle says. Don't add features, screens, settings or "nice to haves". When code and spec disagree, the spec wins.
2. **Stay inside the regeneration boundary.** Create, edit or delete files only under the target's `generated.include` roots (minus `generated.exclude`) in `harness/targets/<target>.json`. Everything else (build files, manifests, configs, lockfiles, theme, other repos) is human-owned scaffold. The harness's boundary gate rejects any change outside the boundary.
3. **No new dependencies.** Use only what the platform profile lists and the scaffold already provides. Never run `npm install <pkg>`, and never edit Gradle files or `package.json`. If something is genuinely missing, stop and explain under `## Blocked`.
4. **No messaging/chat SDKs and no test hooks in production code.** Offline behavior is simulated by the server portal; clients only see real network failures.
5. **Every source file starts with a header comment:** `@generated by chatgen-harness from spec/. Do not edit; change the spec and regenerate.`
6. **Determinism of structure.** Follow the platform profile's architecture and package/folder layout exactly, so that two generations produce comparable code.

## Procedure

### 1. Prepare (interactive only; headless runs have already done this)

```bash
node harness/regen.mjs <target> --prepare-only
```

This deletes the generated roots and writes the composed spec to `harness/runs/latest-<target>/spec-bundle.md`.

### 2. Read, in this order, completely

1. `harness/runs/latest-<target>/spec-bundle.md`: core, enabled features, the platform profile, schemas and scenarios.
2. `harness/targets/<target>.json`: boundary, test locations, gate commands.
3. The vendored skills listed in the target's `skills` array. They're advisory: where they conflict with the profile, the profile wins.
4. Whatever scaffold files the profile's "Scaffold contract" mentions, to learn the exact names, versions and entry points available (for example `package.json`, `libs.versions.toml`, `app/build.gradle.kts`, the manifest and the theme). Read them; don't edit them.

### 3. Plan

Map every requirement tagged `[client]` to the unit that implements it and the test that will verify it, and every `[ui]` requirement to the screen element that realizes it. Keep this map in your task list. Any requirement left without a home is a gap that must be closed before you finish.

### 4. Implement (inside the boundary only)

Build from the inside out, following the platform profile's layer table:

1. **Domain:** types, name and body rules, ordering (REQ-ORDER-*), and merge/status rules (REQ-MSG-001, REQ-SYNC-002). Keep these pure.
2. **Data:**
   - The API client: exact paths, headers, status mapping (REQ-PROTO-*).
   - Persistent stores, with atomic writes (REQ-PERSIST-001).
   - The **sync engine**, implementing the normative pseudocode in `40-connectivity.md` literally: flush before sync, the fixed backoff table, wake semantics and timeouts.
3. **UI:** the three screens, with every element ID, label, placeholder and exact string from `50-ui.md`, exposed through the profile's test-ID mechanism.
4. **Entry points** required by the scaffold contract.

### 5. Test

- Write unit tests at the profile's test location. Every `[client]` requirement ID MUST appear in the name or a comment of at least one test that actually exercises it. The traceability gate checks this.
- Cover the hard parts thoroughly:
  - FIFO and single-flight flush.
  - 400/409 → `failed`.
  - Network failure → `offline` + backoff 1/2/4/8 s.
  - Wake interrupting both the backoff sleep and the long-poll.
  - Flush-before-sync on reconnect.
  - Upsert by id, including an outbox entry whose acknowledgement was lost.
  - Cursor persistence.
  - Both ordering rules.
  - Validation strings.
- Use fakes and virtual time. No real network or sleeps in unit tests.

### 6. Self-verify

Run every command in the target descriptor's `gates` from the project directory, and fix the code until they all pass. On Windows Android builds, use `gradlew.bat` (or `./gradlew` from Git Bash). The harness sets `TEMP`/`TMP` for Gradle.

Before finishing, also check:

- Every element ID in `50-ui.md` is present (search for each one).
- Every exact string matches character for character.
- No file outside the boundary changed (`git -C <project> status`).

### 7. Review

Ask the `spec-conformance-reviewer` sub-agent to review the target. Fix every finding marked **violation**, then re-run step 6.

### 8. Report

Summarize:

- The files you created.
- The gate commands you ran, with their results.
- `## Spec ambiguities`: places where you had to interpret the spec. A human uses this list to tighten the spec.
- `## Blocked`, if anything blocked you.

Do **not** commit. A human reviews and commits generated code.
